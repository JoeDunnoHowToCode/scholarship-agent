## 1. 持續整合：每次推送都在乾淨的環境跑一次檢查（段 1）

**問題**：之前每次推上 GitHub 前，都靠我記得在本機跑 `pytest`、`ruff`、`mypy`、`npm run build`。例如有一次 mypy 的錯誤被 `tail` 吃掉、照樣 commit 了，沒有任何東西擋下來。而且本機的資料庫裡有幾百筆真的資料，測試「在空的環境能不能過」從來沒人驗證過。

**設計**
- GitHub Actions 每次推送到 main 都跑兩個工作（ADR-099）：
  - 後端：開 PostgreSQL（和本機同一個 pgvector 映像）和 Redis → 照 `uv.lock` 安裝 → 遷移 → 種子 → 範例資料 → 測試、ruff、mypy。
  - 前端：照 `package-lock.json` 安裝 → 型別檢查與建置。
- 先在本機開一個空的資料庫 `scholar_ci` 模擬，找到 2 個只讀的測試需要「已經有獎學金和通知」。不改它們，另外加一個建虛構範例資料的指令，裡面不是從任何網站抓的內容，因為 repo 是公開的。
- 用到的 actions 都固定到某個 commit；太新（不到兩週）的版本先不用。這是供應鏈安全，和 `npm ci` 照 lockfile 安裝是同一個道理。
- CI 裡沒有任何金鑰：測試本來就不呼叫真的 AI 和網路。
- 結果：第一次就過，後端 50 秒、前端 13 秒。
- 放棄的做法：本機推送前自動檢查（可以用 `--no-verify` 略過，履歷上也不算 CI）。

**概念**
- **持續整合（CI）**：每次改動都自動在乾淨的機器上建置和測試，問題越早發現越便宜。例子：本機資料庫有資料、CI 是空的，一跑就抓到 2 個依賴本機資料的測試。
- **服務容器（service container）**：CI 裡臨時開的資料庫、Redis，跑完就丟。例子：`services: postgres` 用的是 `pgvector/pgvector:pg17-trixie`。
- **可重現的安裝**：照 lockfile 裝，每次裝到的版本都一樣。例子：`uv sync --frozen`、`npm ci`。
- **固定到 commit（pin）**：tag 可以被改指到別的程式碼，commit 不行。例子：`actions/checkout@3d3c42e…  # v7.0.1`。
- **測試資料的獨立性**：測試不該依賴某台電腦上剛好有的資料。例子：`ci_sample_data.py` 讓空的資料庫也有測試需要的最少資料。

**程式碼導讀**
- `.github/workflows/ci.yml`：兩個工作。後端的 `services`、`env`（只有連線網址、沒有金鑰）、`steps`（遷移、種子、範例資料、檢查）。
- `backend/scripts/ci_sample_data.py`：虛構的範例資料，重跑不會重複。

**你可以怎麼講**：「我用 GitHub Actions 做了 CI：每次推送都在乾淨的 Ubuntu 上開 PostgreSQL 和 Redis 容器，跑遷移、種子，再跑 313 個測試、靜態檢查和前端建置。先在本機用空的資料庫模擬，找到兩個依賴開發資料的測試，用虛構的範例資料解決，沒有把爬到的內容放進公開 repo。用到的 actions 都固定到 commit，避免供應鏈攻擊。」

講的時候分清楚：要做 CI、用 GitHub Actions 是你的決定（ADR-099）。範例資料的做法、固定到 commit、不用太新的版本，是 AI 的實作決定（「Claude 自行決定」第 5、7、8 點）。

**自我檢查**
1. 為什麼本機測試全過，CI 上卻可能失敗？這次遇到的是哪一種？
2. `uses: actions/checkout@v7` 和 `uses: actions/checkout@3d3c42e…` 差在哪裡？
3. 為什麼不直接把開發資料庫匯出一份給 CI 用？

## 2. 評估程式：同一套流程、不同模型、不寫資料庫（段 2）

**問題**：要比較 Gemini 3.5 和 3.1 Flash-Lite 哪個比較好，最直接的做法是「換模型、重抽一次」。但這樣正式資料就被改掉了；兩個模型的結果也沒辦法並排比較；而且網頁可能剛好改版，兩次看到的原文不一樣。

**設計**
- **重構**：把 `extract_source` 裡「抽取、核對、組出結果」拆成 `build_extraction`，它只算、不寫資料庫；`extract_source` 改成呼叫它再存檔。
  - 照重構的規則：先寫 pin 測試釘住現在的行為（馬上通過、單獨 commit）。
  - 重構前後各跑一次完整測試，都是 314 passed。
- **評估指令**：
  - 固定樣本：所有非 Erasmus 的來源，加上用固定亂數種子挑的 40 個 Erasmus 學程，共 57 個，存檔以後每次都用同一批。
  - 用已存的快照，兩個模型看到的原文完全一樣。
  - 每個模型各抽兩次，量得到穩定度。
- **指標都是純函式**（有單元測試）：有根據率、不完整率、穩定度、一致率；不一致清單每個來源最多 1 筆、總共最多 10 筆，讓抽查涵蓋不同來源。
- **報告只放數字**，進 git；原始結果和抽查清單有原文引用，存在本機、不進公開 repo（ADR-098）。
- 放棄的做法：直接用正式的抽取指令換模型重抽，會改到正式資料，也沒辦法並排比較。

**概念**
- **離線評估（offline evaluation）**：在不影響正式系統的情況下，用固定的資料比較不同版本。例子：`run_one` 跑完就把交易復原，資料庫什麼都沒寫。
- **控制變因**：比較時只改一個東西。例子：同一批來源、同一份快照、同一版提示詞，只換模型。
- **固定亂數種子**：亂數挑樣本，但每次挑到同一批，結果才能重現。例子：`random.Random(11)`。
- **穩定度**：同一個模型、同一份輸入跑兩次，結果一不一樣。AI 不是每次都給同樣答案，不穩定的欄位就算「有根據」也不可靠。
- **回歸評估**：之後改提示詞或換模型，再跑一次同一套，確認沒有變差。

**程式碼導讀**
- `backend/app/features/scholarships/extract.py` 第 389 行 `build_extraction`：只算、不寫資料庫。
- `backend/tests/test_extract_build.py`：重構前先寫的 pin 測試（假的 AI、暫存的網頁檔，CI 也能跑）。
- `backend/app/features/evaluation/metrics.py`：第 17 行 `grounded`，第 37 行 `agreement`，第 47 行 `disagreements`。
- `backend/app/features/evaluation/run.py`：第 48 行 `pick_sample`，第 140 行 `disagreements_markdown`，第 186 行 `run_one`（跑完復原交易）。

**你可以怎麼講**：「為了比較兩個模型，我先把抽取流程重構成『只計算、不寫資料庫』的函式：重構前先寫測試釘住行為，前後完整測試結果都一樣。評估用固定亂數種子挑出 57 個來源、用同一份已存的網頁快照，讓兩個模型各抽兩次，算有根據率、穩定度和兩模型一致率；原始結果含網站原文，所以只把數字報告放進公開的 repo。」

講的時候分清楚：用替代指標加抽查、原始結果不進 git 是你的決定（ADR-098）。重構的拆法、57 個樣本怎麼挑、指標怎麼算、不一致清單怎麼選，是 AI 的實作決定（「Claude 自行決定」第 1–4 點）。

**自我檢查**

2. 重構時為什麼要先寫一個「馬上就會通過」的測試？
3. 為什麼要同一個模型抽兩次？只抽一次會漏掉什麼？
