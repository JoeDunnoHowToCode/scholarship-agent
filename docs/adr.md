# 架構決策紀錄（ADR）

使用者決定，Claude 記錄。說明選項的格式見 `docs/decision-format.md`。新的決定往下追加，編號接續。

- 品質屬性（每個決策的取捨依據）：盡快做出能用的版本、學習價值與作品集、結果準確可信
- 限制條件（一定要守，不拿來取捨）：每月 AI 費用上限 NT$7,000（ADR-049，原本 NT$100）；不送可識別個人的資料到雲端

## 已決定

### ADR-001 品質屬性與限制
- 決定：三個品質屬性如上；「盡量免費」與「個資不外流」列為限制條件
- 後果：每個決策都要說清楚為了哪個屬性犧牲了哪個；最常見的衝突是「快」與「學」

### ADR-002 Agent 自主程度
- 決定：混合。抓取、抽取、評分、通知是固定工作流；只有「發掘新來源」是自主 agent
- 後果：agent 只能產生候選來源，必須經使用者核准才加入每日檢查

### ADR-003 執行單元
- 決定：API（FastAPI）與背景 worker 分成兩個程序，共用資料庫
- 後果：程序間靠任務佇列溝通；本機要能一個指令啟動全部

### ADR-004 背景工作
- 決定：任務佇列（Redis）
- 後果：工作必須冪等；排程器只負責放工作，而且只能有一個

### ADR-005 程式分層
- 決定：依功能切模組；只對模型、通知、網頁抓取定義插座與轉接頭；資料庫不額外抽象
- 後果：功能之間不直接 import 彼此的內部

### ADR-006 佇列函式庫
- 決定：RQ，定時排程用 rq cron
- 後果：每種工作要明確設定重試次數與間隔

### ADR-007 Agent 框架
- 決定：主流程用一般 Python 函式，由 RQ 串接；LangGraph 只用在發掘 agent
- 後果：發掘 agent 等待核准時，狀態存進 PostgreSQL 的斷點紀錄，核准後由新的工作接續

### ADR-008 準確度設計
- 決定：抽取後加驗證者，檢查截止日、台灣籍、學位能否在原文找到依據
- 後果：找不到依據就標「待確認」；先驗證這三個欄位，評估證明有效再擴充

### ADR-009 模型供應順序
- 決定：先用使用者自己的 API 金鑰（BYOK），本地模型延後
- 後果：之後加本地模型只需要在 core/llm 加一個轉接頭

### ADR-010 模型存取層
- 決定：LangChain 的模型整合，包在 core/llm 的轉接頭裡；第一版只實作 Gemini
- 後果：鎖定 LangChain 版本；其他供應商等有金鑰、能測試時再加

### ADR-011 結構化輸出
- 決定：原生 schema 為主；Pydantic 驗證失敗時把錯誤回饋給模型重試，最多 2 次
- 後果：可能缺的欄位允許 null 或 unclear；關鍵欄位附逐字 evidence，由程式確認引用存在於原文

### ADR-012 個資處理
- 決定：第一版只用表單輸入條件，不做履歷上傳；只送評分需要的條件
- 後果：去識別排入公開版前的待辦；Gemini 使用付費方案（內容不用於改善產品）

### ADR-013 成本控制
- 決定：記錄每次呼叫的 token 與費用；依「內容雜湊＋提示詞版本＋模型」快取；每月上限 NT$100，超過就暫停 AI 步驟並發 Telegram 通知
- 後果：提示詞改動必須更新版本號

### ADR-014 決策節奏
- 決定：最後負責時刻。做到某一部分之前，才決定那部分的題目
- 後果：每天開工前，先處理下方「待決定」中排在當天之前的題目

### ADR-015 第一版模型
- 決定：Gemini 3.5 Flash-Lite，模型名稱放在設定檔
- 後果：第 10 天用評估資料集和 Gemini 3.1 Flash-Lite 實測比較

### ADR-016 資料庫
- 決定：PostgreSQL，用 Docker 執行
- 後果：和 Redis 一起用 Docker Compose 啟動；LangGraph 斷點紀錄用 PostgreSQL 版

### ADR-017 ORM
- 決定：SQLAlchemy 2.0，結構變更一律用 Alembic 遷移；第一版用同步 Session
- 後果：資料表類別與 API 用的 Pydantic 模型分開，互相轉換

### ADR-018 資料結構
- 決定：混合。截止日、國家、學位、台灣籍、分數等篩選用欄位，完整抽取結果存 JSONB
- 後果：兩處資料在同一個交易裡寫入

### ADR-019 原始資料保存
- 決定：原始 HTML 與 PDF 存在 `backend/data/snapshots/`，資料庫記路徑與內容雜湊
- 後果：不進 git，要定期備份；改提示詞後可以重新抽取

### ADR-020 變更歷史
- 決定：覆寫目前資料，另以變更紀錄表記錄重要欄位的舊值與新值
- 後果：覆寫與變更紀錄在同一個交易裡寫入；需要舊版本時從原始快照重抽

### ADR-021 多人資料隔離
- 決定：profiles、matches、events 三張表加 user_id，第一版固定為 1
- 後果：存取個人資料的函式一律把 user_id 當必要參數

### ADR-022 工程設定
- 決定：只測核心邏輯（評分規則、日期解析、去重）；ruff＋mypy；單一 repo＋uv；Docker 只跑 Redis 與 PostgreSQL，程式原生執行
- 後果：抓取與流程串接先靠手動驗證，痛了再補整合測試

### ADR-023 資料收集與使用者隔離（原則）
- 決定：收集是後台的共用工作，結果只存一份；使用者只讀共用資料，加上自己的條件、評分與通知
- 後果：公開版時個人化評分的成本會隨「使用者數 × 獎學金數」成長，要先用規則篩選，只對前幾名或使用者點開時才請 AI 寫理由

### ADR-024 資料表建立時機
- 決定：資料表在用到的那一天才建立，每次用新的 Alembic 遷移加上；第 1 天只建 scholarships
- 理由：依 ADR-014；sources、snapshots、events 等表的結構要看 #11、#15、#16、#24 等待決定題目，先建就是先猜
- 後果：user_id（ADR-021）要到建 profiles 那天才驗證；每天的計畫要列出當天新增的表與遷移

### ADR-025 主鍵型別
- 決定：所有資料表的主鍵用整數自動遞增（bigint identity）
- 理由：最簡單、好讀、好除錯；單人本機版沒有網址被逐筆猜的風險
- 後果：網址看得出資料順序；公開版若要防止被逐筆猜，另加 public_id（UUID）欄位，不改主鍵

### ADR-026 來源設定的存放方式（#15）
- 決定：全部放資料庫（sources 表）；種子來源寫在遷移或 seed 指令裡（進 git），之後的新增與修改都在資料庫
- 理由：API（設定頁）與 worker（agent）是兩個程序，共用資料庫（ADR-003），資料庫本來就處理同時寫入；發掘 agent 的候選來源、使用者核准、LangGraph 的暫停狀態都在同一個 PostgreSQL（ADR-002、007、016）；唯一限制能擋掉 agent 重複提出的同一個網址
- 後果：執行時的修改不在 git 裡，需要看修改歷史時再另外記錄；跨程序接續 LangGraph 的暫停狀態，第 9 天實作時要實測

### ADR-027 網頁與文件抓取工具（#11）
- 決定：httpx 抓取；BeautifulSoup 取出全部可見文字（不用正文擷取）；PDF 用 pdfplumber；無頭瀏覽器等遇到需要 JavaScript 的來源時，再以 core/fetch 的轉接頭加入
- 理由：三個種子都是伺服器渲染，一般 HTTP 就抓得到；實測正文擷取（trafilatura）會刪掉 EACEA 的學程清單和 Chevening 的「已截止」；pdfplumber 能抽出教育部 PDF 的中文與表格，MIT 授權
- 後果：選單、頁尾等雜訊也會送給 AI（EACEA 一頁約 6 千 tokens）；被 HTML 標籤切開的字（例如「202 7」）要在正規化時處理；sources 表的「抓取方式」記錄哪個來源需要瀏覽器

### ADR-028 爬蟲禮儀與合規等級（#16）
- 決定：用 httpx 的預設 User-Agent（不標明專案，先不加 From 標頭），並守三條界線：一、用 Protego 依 RFC 9309 遵守 robots.txt；二、每個網站限速，內容沒更新就不重新下載；三、不升級手段，被擋（403、429、驗證碼）就停下來標記「需人工」，不偽裝成瀏覽器、不破解驗證碼
- 理由：使用者只做非商用的資訊匯總，目標是全自動；實測 Chevening 會切斷自訂名稱的連線，httpx 預設名稱可以；三個種子的 robots.txt 都允許抓取
- 後果：網站管理者聯絡不到我們，之後要加 From 標頭只改 core/fetch 一處；公開版要顯示內容時，依各來源授權註明出處（EACEA 為 CC BY 4.0，教育部為政府資料開放授權條款）

### ADR-029 第 2 天的抓取範圍
- 決定：第 2 天只做第 1 層，抓 3 個種子（Chevening 台灣頁、教育部 115 年簡章 PDF、EACEA 目錄含翻頁）；學程網站的第 2、3 層（學程首頁、申請與獎學金頁）等第 3 天和 #13 一起決定
- 理由：依 ADR-014；實測學程首頁沒有截止日，需要的資訊在第 3 層，而「怎麼找到正確的頁面」本來就是抽取策略（#13）的一部分
- 後果：第 2 天結束時還沒有學程的實際資料；#13 要一併決定學程網站第 2、3 層怎麼找（關鍵字比對或 AI 挑連結）

### ADR-030 抓取時的憑證檢查
- 決定：所有網站照常做憑證的基本驗證（信任鏈、網域名稱、有效期限），但關掉 Python 3.13 預設開啟的嚴格格式檢查（VERIFY_X509_STRICT）
- 理由：教育部憑證鏈的根憑證 TWCA Global Root CA 缺少 Subject Key Identifier 欄位，嚴格檢查會拒絕連線；Python 3.12 以前預設不開這項檢查（兩個版本都實測過）
- 後果：所有網站都少了這層格式檢查；實測過期、網域不符、自己簽發的憑證仍會被拒絕

### ADR-031 抽取策略（#13，含學程網站第 2、3 層）
- 決定：混合。格式固定的清單頁用專屬解析器（EACEA 目錄 → 學程名稱與網址）；內容頁交給 AI 照 schema 抽取（學程網站、Chevening、教育部 PDF）；學程網站的第 3 層由 AI 從首頁連結挑出申請與獎學金頁
- 理由：EACEA 目錄格式固定，程式能精確列出學程；學程網站格式各異、寫法多樣（例如截止日寫成「application period … 15th January 2027」），需要 AI 讀；實測關鍵字比對在大網站會多抓、在非英文網站會漏抓
- 後果：兩套做法都要維護；EACEA 改版時解析器要修，而且要能發現解析器壞掉；挑連結是新的一種 AI 呼叫，要設計與驗證；AI 抽出的關鍵欄位仍由驗證者核對原文依據（ADR-008）

### ADR-032 第一版加入 RAG：搜尋與問答（#23）
- 決定：第一版加入兩種 RAG：用一句話搜尋獎學金，以及對抓下來的原文提問、回答附出處。因此需要向量檢索（#23）：每筆獎學金一個向量（搜尋、去重），原文切段後每段一個向量（問答）。切段做成之後長文件都能套用的通用流程
- 理由：使用者手上沒有 RAG 的專案，想多練 RAG 與 agent；用描述搜尋、附出處的問答，都對找獎學金有幫助
- 後果：spec 第一版範圍變大，排在哪一天待決定（#46）；切段方式、向量存放、問答做成固定流程或 agent 都待決定（#47–49），做成 agent 會牽動 ADR-002、007；費用粗估：原文建向量一次約 NT$5，問答每題約 NT$0.07

### ADR-033 RAG 排在新的第 5 天（#46）
- 決定：在原本的第 4 天之後新增一天專門做 RAG（通用切段、向量、用一句話搜尋、問答附出處），先用指令操作；原本的第 5–10 天各往後一天，共 11 天
- 理由：第 4 天去重、整理好申請期之後，搜尋用的資料最完整；RAG 有一整天可以專心做
- 後果：第一次能用（評分清單）從第 5 天延到第 6 天；搜尋與問答的網頁介面在第 9 天（原第 8 天）接上；待決定題目的時間跟著往後一天

### ADR-035 問答的範圍
- 決定：問答兩種都做：單一文件模式（使用者指定一份文件，整份交給 AI 回答）與全部資料模式（所有快照切段、建向量，先檢索再回答，附出處）
- 理由：使用者兩種問法都會用，也想練完整的 RAG
- 後果：第 5 天工作量最大；檢索方法、切段方式（#47）、向量存放（#48）都要配合全部資料模式；PDF 轉文字與表格處理另列待決定（#50）

### ADR-036 表格的處理方式（#50 的一部分）
- 決定：四種並用：A 整格表格自成一段；B 由 AI 替每個表格寫一句說明，用說明建向量、命中時取回整格；C 每段標上類型與主題（名額、資格、金額、截止日、文件……），提問時先篩主題再檢索；D 名額等精確數字存成資料表欄位，直接查詢
- 理由：表格攤平成文字會失去列與欄的對應（實測教育部名額表的國家名單被換行切斷），使用者要求表格相關的問答要正確
- 後果：需要先偵測表格（PDF 用 pdfplumber 偵測，網頁看 table 標籤）並轉換正確；每個表格多一次 AI 呼叫寫說明；每段要標主題；使用者接受每份 PDF 約 NT$3 交給 Gemini 讀原檔的費用；PDF 轉文字的方式另外決定（#50）

### ADR-037 PDF 轉文字：Gemini 轉錄加 pdfplumber 原文核對（#50）
- 決定：PDF 交給 Gemini 讀原檔，轉成保留表格的格式，供切段、表格處理與 RAG 使用；pdfplumber 取出的原文當核對基準，Gemini 版本裡的每個數字與引用都必須在原文找得到，找不到就標「待確認」
- 理由：Gemini 看得懂表格與版面；pdfplumber 取的是 PDF 原文、不會改字，可以抓出 AI 轉錄漏字或改字
- 後果：每份 PDF 轉一次約 NT$3，只有改版才重轉；兩套轉換都要維護；網頁不受影響（表格用 table 標籤）

### ADR-038 通用切段方式：依結構（#47）
- 決定：依結構切段：PDF 依「一、」「(一)」這類編號，網頁依 h1–h4 標題；表格自成一段（ADR-036）；太長的段再依長度細切，太短的併到前一段
- 理由：每段是一個完整主題，問答出處能寫成章名；和「一章一章抽取」（ADR-034）對得上；表格本來就是結構的一部分
- 後果：PDF 和網頁各一套切段規則，編號寫法不同的文件要加規則；沒有結構的文件退回依長度切；段落長度上下限在第 3 天計畫裡訂

### ADR-034 長文件抽取用切段（#12）
- 決定：長文件抽取時，用通用切段流程切開，一段一段抽，再由程式合併；一般網頁仍整頁讀
- 理由：使用者想讓同一套切段流程同時用在抽取和 RAG；每次輸出短，單段抽取比較準
- 後果：切段流程提前到第 3 天做，切段方式（#47）因此改成第 3 天前決定；要寫合併規則，例如把總則（教育部簡章第 3 章的學位限制）套回各個名額類別，規則漏寫會讓欄位變成「不確定」甚至錯誤；「多長算長文件」在第 3 天計畫裡訂

### ADR-039 第 3 天的做法：分階段做完
- 決定：第 3 天的範圍不拆天、不往後移，分階段實作；需要使用者決策的功能先不做完，問題統整到最後的報告，其他不受影響的部分繼續做
- 理由：使用者希望一次推進到底，不要每遇到一個問題就停下來；小問題由 Claude 決定並記錄，只有產品與架構的選擇才問使用者
- 後果：第 3 天可能不只一次工作時段；Claude 自行決定的小問題記在 `docs/day-03.md`，使用者事後檢查

### ADR-040 一份簡章多個類別：獎學金表加類別表
- 決定：scholarships 一筆代表一個獎學金計畫；新增 scholarship_categories 表，每個名額類別一筆（名額、學位、資格、留學國家等）
- 理由：教育部留學獎學金一個計畫有 8 個類別、條件各不相同，第 6 天評分要知道使用者符合哪一個類別；ADR-036 D 的名額欄位放在類別表
- 後果：只有一個類別的獎學金也有一筆類別；第 6 天評分與第 8 天通知要以類別為單位判斷；共同資訊（金額、報名時間）只存一次

### ADR-041 第 3 天跑完全部學程網站
- 決定：EACEA 目錄的 218 個學程網站，第 3 天全部抓取與抽取
- 理由：第 3 天結束就有完整的學程資料
- 後果：一次約跑 1–2 小時；第一次建檔的 AI 費用估計 NT$25–40；做法若有問題，要修正後重跑（快照已存，重抽不必重新下載）

### ADR-042 Gemini 用付費方案，加上限速器
- 決定：Gemini API 改成付費方案（使用者已設定帳單）；Gemini 轉接頭加每分鐘請求數上限，數字放在設定檔
- 理由：免費方案的內容可能被拿去改善產品，和 ADR-012 衝突；第 3 天實跑時撞到免費方案每分鐘 15 次的上限（同時開了 5 個程序）；限速器之後也能防止撞到付費方案的上限
- 後果：開始實際付費，仍受每月 NT$100 上限約束（ADR-013）；限速器只管單一程序，平行跑 N 個程序時總量是 N 倍，要一起算

### ADR-043 國籍資格改成依國籍判斷
- 決定：獎學金不再存「台灣籍能否申請」，改存國籍資格：範圍（開放所有國籍、只限列出的國家、排除列出的國家、沒寫）＋國家清單＋原文引用；使用者在個人資料填國籍，評分時由程式比對。開放所有國籍視為可以申請；原文沒寫國籍資格才是待確認。180 筆全部重新抽取
- 理由：專案之後可能給其他國籍的人用（作品集、公開版），現在改只要改抽取與資料表；等到評分、網頁篩選都寫好再改，要多改 1–2 天、重抽的資料也更多
- 後果：spec 的「台灣籍資格」「台灣專屬條件」改成國籍資格與國籍附加條件；第 6 天評分要讀使用者的國籍並處理國名寫法（例如 Taiwan、Republic of China、Chinese Taipei）；這次重抽約 NT$20

### ADR-044 學程網站的 PDF：缺資料才讀，照 ADR-037 轉錄
- 決定：學程抽完後，截止日或文件清單有缺，才從它的頁面找和申請相關的 PDF 連結來讀；讀法照 ADR-037（Gemini 轉錄＋pdfplumber 原文核對）
- 理由：178 個學程中 62 個有和申請相關的 PDF，其中 26 個剛好缺資料；只讀缺資料的，費用約 NT$5–25；pdfplumber 不會 OCR、表格會錯位（ADR-036、037 的理由）
- 後果：網頁上已有截止日、但 PDF 裡有更細規則的學程不會去讀；每個學程最多讀幾份、多少頁由 Claude 訂在第 3 天補強計畫

### ADR-045 抽取穩定度：程式檢查與格式限制；溫度無法調整
- 決定：加五條程式檢查（截止日年份要在引用裡、學位要在原文寫到、類別名稱要在原文而且不能太長、名額要在原文找得到、名額加總要等於總額），不符合就標待確認；格式限制兩種：第二輪抽取的類別名稱改成選單（列舉）、截止日拆成年月日（年份允許空白）
- 理由：實驗發現錯誤大多每次都犯在同一處（教育部北歐、新南向每次都被加上 bachelor），程式檢查最擋得住；截止日年份錯了會把去年的申請期當成今年的
- 後果：實驗時 LangChain 回報 gemini-3.5-flash-lite 使用固定的取樣設定、會忽略 temperature，所以溫度不是可調的選項；#45（評分的溫度）在這個模型上也不必決定，換模型時再看

### ADR-046 學位的附加條件另存一欄
- 決定：類別的學位清單列出所有可能讀的學位（包括要符合條件才能讀的），條件另存成文字欄位 degree_conditions（例如「碩士限藝術學群、建築規劃與設計學群」），條件寫出來給人看；第 6 天評分時，有附加條件的學位算「待確認」。同時把每個類別的原文引用拆成名額引用與學位引用
- 理由：學位欄位只是清單，表達不了條件；教育部北歐國家原則上只能讀博士、藝術與建築學群例外，清單只能在「只有博士」和「碩士、博士」之間二選一，兩種都會誤導；使用者要申請碩士，這個判斷直接影響結果。追查根本原因時發現，名額與學位共用一格引用，模型只引用名額那句，學位因此沒有依據
- 後果：scholarship_categories 多一個欄位；評分不會自動判斷使用者的學群，只標待確認；提示詞改版，其他學程要等下次全部重抽才有新欄位（本月 AI 額度接近上限，排到 11 月）

### ADR-047 申請期：一屆可以有多個截止日，各附結構化的適用對象
- 決定：申請期（cycles）一屆可以有多筆，每筆有開放日、截止日（UTC 加原始時區）、狀態，以及結構化的適用對象：國籍範圍（沿用 ADR-043 的 all／listed／excluded＋國家清單）與申請類型（申請獎學金／自費／不限），另有一段說明文字（例如「第一輪」「Partner countries」）
- 理由：實際資料常見同一屆依申請人分組的不同截止日（學程 20：夥伴國 2/28、歐盟國 3/31；學程 35：獎學金 2 月中、自費 4 月底），178 個學程中約 69 個提到這類分組或輪次；結構化之後，評分與提醒能依使用者的國籍自動挑出屬於他的截止日
- 後果：抽取表格的截止日從一組年月日改成一個清單，AI 要填的格子變多，可能填錯；合併、驗證、程式檢查都要改成逐筆處理；180 筆要重抽

### ADR-048 去重：第 4 天先用規則，第 5 天加向量
- 決定：第 4 天用規則判斷重複（官方網址正規化後相同，或提供單位＋名稱正規化後相同）；第 5 天有向量之後，再加上相似度比對（ADR-032）
- 理由：第 4 天就有基本去重；向量要等第 5 天
- 後果：規則只抓得到寫法幾乎一樣的重複；名稱必須帶上學程名稱才能拿來比對（實測有 5 個不同學程的獎學金都叫「Erasmus Mundus Scholarships」），提示詞要改並重抽

### ADR-049 每月 AI 費用上限改為 NT$7,000
- 決定：每月 AI 費用上限從 NT$100 改為 NT$7,000（使用者已在 Google AI Studio 設定），每個月都適用；取代 ADR-001 裡「每月 NT$100」的限制條件
- 理由：使用者決定提高預算，讓重抽、實驗與之後的功能不被每月 NT$100 卡住
- 後果：ADR-013 的「超過上限就暫停 AI 步驟」（第 10 天）改用 NT$7,000；上限是最後一道保險，程式出錯一直重複呼叫 AI 時，最多可能花到這個金額才停，所以每次執行指令仍用 `--max-cost` 設一個低很多的上限；成本取捨（例如較強的模型、投票）的空間變大

### ADR-050 向量存放：pgvector（#48）
- 決定：向量存在現有的 PostgreSQL，用 pgvector 擴充功能；Docker 映像檔換成 `pgvector/pgvector:pg17`
- 理由：獎學金、申請期、段落和向量在同一個資料庫，一個 SQL 就能同時篩條件（開放中、國籍）和做語意搜尋；同一個交易寫入，不會不同步；只有一個資料庫要備份
- 後果：pgvector 的索引最多 2,000 維，Gemini 的向量要縮到 1,536 或 768 維（或改用 halfvec）；向量旁要記嵌入模型與維度，換模型要全部重算；沒有學到獨立向量資料庫的同步問題

### ADR-051 問答：路由（#49）
- 決定：問答用路由：先由 AI 判斷問題類型並抽出參數，再走固定路線（查某一筆、條件篩選、語意搜尋、單一文件）；不讓 AI 寫 SQL，只填篩選條件表格；分類不確定或查不到時退回語意搜尋；每條路線的答案都附出處
- 理由：常問的問題答案分在不同地方（類別表、申請期表、文件清單、原文段落），單一流程答不完整；路由仍是固定流程，可預測、好測試，符合 ADR-002；每條路線之後可以直接變成 agent 的工具
- 後果：要寫分類與四條路線；分類錯了會走錯路，要用固定題目評估分類準確率（#30）；ADR-002、007 不變

### ADR-052 問答不綁定模型，公開版前再選
- 決定：問答程式只透過 core/llm 的插座呼叫模型（ADR-005、009），第一版用 Gemini；給其他使用者用的問答要用哪種模型（Gemini 加使用量限制、Ollama 本地模型、混合、使用者自帶金鑰、雲端開源模型服務），等公開版前（#44）再決定
- 理由：第一版只有使用者本人；實測這台 M4、24 GB 的 Mac 用 qwen2 7B 回答一題約 101 秒，答案還自相矛盾，本地模型的速度與品質要等新模型與公開版的需求再評估
- 後果：問答的程式不能直接用 Gemini 專屬的功能；之後換模型只要加轉接頭；向量的嵌入模型要和建索引時同一個，問句與原文不能用不同模型

### ADR-053 EACEA 學程的國籍依據：目錄頁的說明
- 決定：從 EACEA 目錄來的學程，自己網站沒有寫國籍資格（沒附引用或引用不支持）時，改用 EACEA 目錄頁的說明當依據，標成開放所有國籍，並註明依據來自 EACEA；學程網站有寫限定或排除的國家，照學程網站。依據原文：「Master's level students from all over the world can apply. Additionally, scholarships are available for outstanding students.」
- 理由：Erasmus Mundus 學程由歐盟統一規範，目錄頁說明全世界的學生都可以申請；不然 80 筆會因為學程網站沒寫而被標待確認，評分上限 80
- 後果：這句話講的是「學程開放全世界申請」，沒有直接寫獎學金不限國籍；某個學程若另有國籍限制但網站沒寫，會判錯；不用重抽，程式改判

### ADR-054 國家一律存 ISO 國碼，抽取時由 AI 讀上下文填寫
- 決定：國家一律存 ISO 3166-1 兩碼國碼（例如 TW、KR、CZ），涵蓋留學國家、國籍清單、申請期的國籍清單、類別的國家；抽取時由 AI 讀整句話直接填國碼，程式用國碼套件檢查代碼存在；Kosovo 沒有正式國碼，用常見的使用者自訂碼 XK；畫面顯示用我們自己的名稱（台灣顯示為「台灣」）
- 理由：國名寫法不一致（Czech Republic／Czechia、North Korea／Democratic People's Republic of Korea）；單看一個字也可能分不出，學程 221 的「Korea」要靠同一串清單裡已經有北韓，才知道是南韓；抽取時 AI 正在讀整句話，最能判斷；向量的語意相似反而會把南韓、北韓當成很像
- 後果：180 筆要重抽（約 NT$40）；Erasmus+ 的 33 國清單改成國碼；個人資料的國籍也存國碼；AI 填了不存在的代碼要丟掉並標記

### ADR-055 評分保留，個人資料最少，門檻只顯示
- 決定：保留 0–100 評分；個人資料必填國籍與想讀的學位，選填目前科系、想讀的領域、想去的國家；不收成績、語言檢定、工作年資、年齡。硬性條件只看國籍、學位、時間；語言、成績、年齡、工作年資等門檻只顯示給人看，不拿來評分或淘汰。AI 分項拿掉「條件達成度」，其他四項依比例調整權重；送給 AI 的個人資料只有科系與想讀的領域
- 理由：使用者的目的主要是讓人搜尋得到、看得到資訊，而不是限縮；使用者不必填很多東西；評分仍負責排序、通知門檻與一句理由
- 後果：spec 的評分規則改寫；不符合語言門檻的獎學金不會被扣分，要使用者自己看門檻資訊；通知門檻 60 分照舊（第 8 天）；個資只送科系與領域，比 ADR-012 原本的範圍更小

### ADR-056 重試、退避與失敗隔離：依錯誤種類處理，加斷路器（#25）
- 決定：每個來源各自一條處理流程，一個來源出錯不影響其他來源。錯誤先分類：暫時性錯誤（逾時、網路斷線、5xx、Gemini 的 429 限速）重試並退避；網站回 429 照 ADR-028 算被擋；永久性錯誤（404、被擋、AI 抽出的資料驗證不過）不重試，記下原因，被擋的照 ADR-028 標需人工。Gemini 額度用完或超過費用上限時打開斷路器，暫停所有 AI 工作，等使用者處理後再恢復
- 理由：不白白重試，額度用完馬上停，避免和 LangChain 內建的重試（每次呼叫最多 6 次嘗試）疊加；這是真正上線系統常見的做法（學習價值與作品集）
- 後果：要寫可以單元測試的錯誤分類函式，以及斷路器的狀態與恢復方式；第 10 天的每月費用上限（ADR-013）共用同一個斷路器；重試由誰執行（RQ 的 Retry 或雲端排程的任務重試）依 #54 決定

### ADR-057 第一版留在本機，雲端部署之後再做（#54）
- 決定：第一版的 worker 與排程都跑在本機；部署到 GCP 延後，使用者之後想練雲端部署
- 理由：先做出能用的版本；不必改限制條件（個資不上雲）和 ADR-003、004、006、007、016、019、022；雲端費用 0
- 後果：電腦白天通常沒連網，排程不能只靠固定時間，要在每天第一次有網路時補跑當天的檢查；背景程式怎麼啟動（每次手動，或登入後自動）另外決定（#54b）；部署路線併入 #44，評估結果記在 #44 的筆記

### ADR-058 預估的下一屆：太舊就不預估（#51）
- 決定：封存的獎學金，最近一次真的截止日在 24 個月內的，預估日期一直加一年直到今天以後，並註明依哪一年的日期推估，從預估開放前一個月起每 7 天回官網檢查一次；超過 24 個月的不產生預估，標成「資料過舊」，原因寫官網最新資訊的年份，每個月檢查一次。使用中的獎學金照常每天檢查
- 理由：不用很舊的資料猜出看起來正常的日期；使用者一眼看得出哪些可能停辦
- 後果：獎學金多一種「資料過舊」的標記，通知（第 8 天）和網頁（第 9 天）要處理；第 7 天的排程依獎學金的狀態決定多久檢查一次（每天、預估前每週、過舊每月）

### ADR-059 評分只算適配度；時程、補助、名額改成只顯示（#53）
- 決定：分數只代表使用者和獎學金合不合：國籍、學位兩個硬性條件（程式判斷，不符合上限 20、待確認上限 80），加上 AI 評的領域契合。時間條件、時程可行、補助價值、競爭與名額都不算進分數，改成顯示。列表依狀態分組：還能申請的在前，已截止但適合你的在後，並顯示預估的下一屆
- 理由：獎學金本身的狀態和條件不是使用者和它的適配度；要評時程還得估準備申請要多久，不是這個專案要做的
- 後果：ADR-055 的「AI 分項四項」和 spec 的評分規則要改寫；AI 每次只評一項；第 8 天「60 分以上才通知」的意思變成「適配度 60 以上」；沒填科系與領域時怎麼評分、想去的國家要不要算進適配度，另外決定（#53b）

### ADR-060 使用者填的資料都要算進評分（#53b）
- 決定：個人資料的每個欄位都要有作用：國籍、學位是硬性條件；目前科系與想讀的領域由 AI 評領域契合；想去的國家由程式比對留學國家，算進適配度。沒填的欄位不評，其他依比例調整；只填了必填的國籍與學位時只看硬性條件：符合 100、待確認 80、不符合 20
- 理由：會讓使用者填的資料，就一定要有作用，不然不該叫他填
- 後果：要新增「想去的國家」的比對與權重（第 7 天的計畫裡訂）；送給 AI 的個資仍然只有科系與領域（ADR-055），國家比對由程式做

### ADR-061 本機背景程式：登入後由 launchd 自動啟動（#54b）
- 決定：用 macOS 的 launchd，登入後自動在背景啟動 RQ worker 與排程器，當掉自動重新啟動；每天第一次有網路時補跑當天的檢查
- 理由：電腦白天通常沒連網，使用者也不必記得手動啟動，最接近「每天自動檢查」的目標
- 後果：會在 ~/Library/LaunchAgents 加登入項目，提供安裝與移除的指令；PostgreSQL 與 Redis 的容器要設定自動重啟，Docker Desktop 要在登入時啟動；日誌寫到 backend/data/logs/；launchd 是 macOS 專用，上雲時（#44）改用雲端的排程

### ADR-062 通知送出模式：Outbox（#24）
- 決定：要通知的事先寫進 events 表（狀態「待送」），再由另一件工作讀出、超過 5 則就合併成摘要、送出、標記「已送」；事件由程式從資料庫裡已經存好的資料（新獎學金、申請期、變更紀錄、評分）產生，每個事件有唯一的去重鍵，重跑不會重複產生
- 理由：不會漏送，查得到每則送過沒有；沒網路時待送的會留著，有網路再送；「剩 N 天只提醒一次」直接查 events 表；第 9 天的網頁可以顯示通知歷史
- 後果：多一張 events 表（有 user_id，ADR-021）和一件送出工作；至少送一次：送出後、標記已送前當掉，可能重複一則。選項 C（每則通知一件 RQ 工作）沒採用，但送出那一步本身就是 RQ 工作

### ADR-063 通知插座：結構化通知（#28）
- 決定：`core/notify` 的插座收一則結構化通知（類型、標題、內容行、連結），由轉接頭負責排版；第一版只有 Telegram 轉接頭，負責轉成 HTML、轉義特殊字元、切成 4096 字以內
- 理由：功能模組不用知道 Telegram 的格式；轉義與切段集中在轉接頭，可以單元測試；加新管道只要寫一個轉接頭
- 後果：多一層資料結構；依事件類型選管道（選項 C）等有第二個管道時再加；通知只放獎學金名稱、分數、截止日與連結，不放會提到科系的理由（ADR-001、012）

### ADR-064 通知只看可能影響能不能申請的變更；官網真的改了才算變更
- 決定：資料變更只有「官網真的改了」才算；推播只看可能影響能不能申請的條件：截止日（含延長）、國籍資格、可讀學位。金額與文件要求的變更不推播，點進詳細頁就看得到
- 理由：金額不影響能不能申請，也是使用者自己會注意的。文件要求公告後很少改，改的時候會有正式公告：第 8 天上網查證，公告後的修改多半是只改一條的勘誤（errata corrige），最常見的變動是截止日延長，規則的大改動多在兩屆之間；我們 189 個來源裡沒有任何勘誤公告。而系統偵測到的金額與文件「變更」，幾乎都是 AI 每次抽取結果不同造成的雜訊
- 後果：通知規則拿掉金額與文件要求；國籍資格變成「原文沒寫」不算變更（官網沒改，只是 AI 漏抽）；判斷官網有沒有真的改，要改成核對原文（新的引用在上一版網頁裡找不到才算），在第 8 天補做；網頁上的動態內容（時間戳）讓整頁每天重抽，另外處理；金額怎麼抽（#55）另外決定

### ADR-065 截止日改到已經過去的日期，不通知
- 決定：截止日的變更，如果同一屆新的截止日都已經過去（早於台灣的今天），就不推播
- 理由：第 8 天發現 ReSound 官網改寫了 2027 屆那句（2027-01-12 截止），AI 卻抽到同一頁 2025/26 屆的句子（2026-01-20），還標成 2027 屆。核對原文（ADR-064）只能確認官網改了，不能確認 AI 抽到的新值對。主辦單位把截止日提前到已經過去的日期很少見，列表上也會顯示已截止
- 後果：判斷要不要通知時要知道今天的日期；真的提前截止到過去的情況收不到通知

### ADR-066 前端框架：React＋Vite 單頁應用（#35）
- 決定：前端用 React＋TypeScript＋Vite 做單頁應用；建置後由 FastAPI 的 `app.frontend()` 提供，做好後仍是一個程式、同一個網址
- 理由：使用者也想練前端（學習價值與作品集）；React 用的人最多（Stack Overflow 2026 用過 41.5%、State of JS 2025 85%）；FastAPI 官方全端範本同一套，有參考結構；FastAPI 0.138 起的 `app.frontend()` 讓 launchd 不用多管一個程式；搭配 #36 在編譯時抓到欄位錯誤
- 後果：要裝 Node 與 npm 套件，鎖定版本、跟安全更新（npm 供應鏈攻擊，CISA 2025-09-23）；開發時兩個伺服器，Vite 把 `/api` 轉發到 FastAPI；第 9 天比 HTMX 慢；完整比較見 `docs/day-09-brief-35.md`

### ADR-067 前後端型別契約：由 OpenAPI 產生型別（#36）
- 決定：用 openapi-typescript 從 FastAPI 的 `/openapi.json` 產生 TypeScript 型別，呼叫 API 用 openapi-fetch；產生的檔案不手改
- 理由：後端改了欄位，重新產生後前端編譯就報錯（結果準確可信）；執行時幾乎沒有額外的程式
- 後果：後端 API 改了就要重新產生；型別只在編譯時檢查，伺服器真的回傳不一樣的東西時發現不了；有預設值的欄位會產生 `?`、日期時間是字串；openapi-typescript 2026-02 之後只有依賴更新，要留意維護狀況

### ADR-068 UI 元件：shadcn/ui 複製進專案＋Tailwind（#37b）
- 決定：畫面元件用 shadcn/ui，需要的元件用 CLI 複製進專案；樣式用 Tailwind 4
- 理由：元件原始碼在專案裡，可以改，不受套件大改版影響；FastAPI 官方範本同一套；學得到 Tailwind 與元件的組成
- 後果：要學 Tailwind；shadcn 的元件之後有更新，要自己決定合不合併；底層元件庫（2026-07 起預設 Base UI，也可選 Radix）在第 9 天計畫裡定

### ADR-069 搜尋：篩選＋混合搜尋（#35b）
- 決定：列表有篩選與排序；搜尋框同時做關鍵字比對（名稱、中文名稱、領域、提供單位）與語意搜尋（第 5 天的 `find`），再用 Reciprocal Rank Fusion 合併名次
- 理由：關鍵字找得到簡稱和字面一樣的字；語意找得到不同說法與中英文（10-25 實測「數據科學」關鍵字 0 筆，語意找到 EMLDS、BDMA、NeuroData）；混合搜尋是 RAG 常見的做法（學習價值）
- 後果：沒網路時只剩關鍵字（電腦白天常沒網路，ADR-057）；搜尋的字會送到 Gemini 算向量，每次不到 NT$0.001，搜尋框不要打個人資料；語意一定會排出結果，不相關的也會出現；合併規則要有測試

### ADR-070 金額：每個金額一筆，附用途與原文引用（#55）
- 決定：抽取表格的金額改成清單，每筆有數字、幣別、期間（每月、每年、一次）、用途（生活津貼、學費、旅費、其他）、適用對象與逐字引用；程式核對引用在原文裡，而且引用裡真的有這個數字
- 理由：列表要顯示有意義的大概數字（使用者的方向），每個數字都能追溯與核對（結果準確可信）；同一幣別內可以排序或篩選。第 8 天發現 188 筆裡 145 筆的官網寫著 2 個以上的歐元金額，一格文字時 AI 每次可能挑不同的
- 後果：改資料結構、抽取表格、提示詞與驗證，全部重抽約 NT$34；列表顯示哪一個數字、要不要換算幣別、原本的金額文字欄位怎麼處理，在第 9 天計畫裡定

### ADR-071 前端資料抓取：TanStack Query（#37a）
- 決定：前端拿資料、改資料都用 TanStack Query（`useQuery`、`useMutation`）；實際呼叫 API 用 openapi-fetch（ADR-067）
- 理由：載入中、錯誤、快取、修改後失效都內建：問答要等好幾秒；改了個人資料後，評分列表要自動重抓；FastAPI 官方範本同一套
- 後果：要學查詢鍵（query key）與失效（invalidation）；路由用 React Router 或 TanStack Router、要不要用 openapi-react-query（約 1 kB，把 openapi-fetch 接到 TanStack Query）在第 9 天計畫裡定

### ADR-072 本機網頁的存取安全：第一版維持現況，登入等公開版（#43）
- 決定：第一版只靠 uvicorn 預設綁 `127.0.0.1`，加上 FastAPI 預設只把 `application/json` 當 JSON 解析；不加 Host 檢查、CORS 設定或權杖。登入（用 Google 登入，公開區＋登入區）等公開版（#44）再做
- 理由：第一版只有使用者本人在本機用，0 工作量；登入的好處主要在公開版
- 後果：和限制條件「個資不外流」有一條沒擋的路：用 Safari（或 Firefox 的保護還沒推到時）逛到惡意網站，DNS rebinding 讀得到個人資料、呼叫得了會花錢的問答；Chrome 94 起會擋這招，Chrome 142 起公開網站連本機要先經過你同意；只靠網址參數的 API 擋不住 CSRF。開發時 Vite 轉發 `/api`、做好後由 `app.frontend()` 提供，都是同一個網址，所以不需要 CORS。公開版或上雲（#44）前必須重新決定

### ADR-073 網頁伺服器手動啟動
- 決定：launchd 照舊只在登入後啟動 worker 與排程器；網頁伺服器（FastAPI）要用時才手動啟動
- 理由：伺服器只有開著的時候，ADR-072 的風險（Safari 上 DNS rebinding 讀得到個人資料）才存在
- 後果：要用網頁時先跑一個指令（第 9 天寫進 CLAUDE.md 的常用指令）；通知與每日檢查不受影響，它們由 worker 執行

### ADR-074 金額只補抽，其他欄位不重抽（第 9 天的重抽 C）
- 決定：既有資料用一個只抽金額的提示詞（amounts-1）補上金額清單，其他欄位不動；補完後把抽取結果記錄的提示詞版本改成最新，之後原文有變才整份重抽。已經被新版整份重抽、但原文沒變的，從 10-27 22:11 的備份補回其他欄位再補金額
- 理由：AI 一次填完整張表，整份重抽會讓已核對的國籍、學位也重新抽一次而變動（教育部的國籍從已核對變成原文沒寫；新版 13 筆對舊版 175 筆：國籍核對通過 92% 對 100%、學位 69% 對 80%）；這次改版只動了金額的規則，其他欄位的規則沒變
- 後果：多一個金額專用的提示詞要維護；「版本記成最新」是 ADR-013 快取規則的例外，只用在改版只動了某些欄位的規則時，並在抽取結果記下金額的來源（amounts_from）；補抽讀快照原文（和核對用的一樣），不另外轉錄 PDF；約 NT$30；備份之前就被整份重抽的 14 筆沒有舊值可補，維持新版（教育部的國籍、學位已標待確認）
### ADR-075 每天的檢查：前一輪還沒收尾，就先不開新的一輪（第 9 天第 3 題）
- 決定：tick 開始今天的檢查前，先看最近一輪收尾了沒；還沒收尾、而且開始不到 48 小時，這次先不開，等下一次 tick 再看。超過 48 小時就當成收尾壞了，照常開新的一輪。收尾和送通知照舊排在佇列最後面（沒有選 C 的插隊）
- 理由：同一時間只有一輪，收尾送出的通知前面沒有新一輪的工作擋著，幾分鐘內就送出；前一輪還在等重試時，同一個來源不會排兩次（第 9 天執行時發現第 2、12 點）
- 後果：今天的檢查最多晚 15 分鐘開始，前一輪在等重試時晚約 30 分鐘；收尾工作壞掉時，最多 48 小時不檢查任何來源；檢查到一半斷路器打開時，那則通知排在剩下的來源工作後面
