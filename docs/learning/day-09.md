## 1. 網頁介面：React＋Vite，由 FastAPI 一起提供

**問題**：資料都在資料庫裡，要打指令才看得到。例如想知道「教育部的獎學金什麼時候截止、要交哪些文件」，得記得指令和參數。

**設計**
- 前端用 React＋TypeScript＋Vite 做單頁應用，建置成靜態檔案後，由 FastAPI 的 `app.frontend()` 一起提供。這樣只要開一個程式、用一個網址，也不用處理跨網域（CORS）（ADR-066）。
- 前後端的型別契約：FastAPI 會自動產生 `/openapi.json`，openapi-typescript 再把它轉成 TypeScript 型別。後端改了欄位，重新產生型別後，前端編譯就會報錯（ADR-067）。
- 拿資料用 TanStack Query：載入中、錯誤、快取都內建。改了個人資料後，讓「個人資料」和「獎學金列表」的快取失效，列表就會自動重抓（ADR-071）。
- 元件用 shadcn/ui：元件的原始碼複製進專案，可以直接改（ADR-068）。
- 放棄的做法：
  - HTMX＋Jinja2：第 9 天能做得比較快，但練不到前端。
  - Next.js：還要多管一個 Node 伺服器。
  - Vue：用的人比 React 少。

**概念**
- **單頁應用（SPA）**：瀏覽器只載入一次網頁，之後換頁都靠 JavaScript 重畫。例子：從列表點進詳細頁，網址變了，整頁卻沒有重新載入。
- **API 契約與型別產生**：前後端對「有哪些欄位、各是什麼型別」共用同一份說明書。例子：後端把 `amount_headline` 改名，前端跑 `npm run build` 就會直接失敗，不會等到畫面上出現空白才發現。
- **伺服器狀態快取**：從 API 拿到的資料先存起來，同一份不重複抓；資料可能過期時，就讓它失效。例子：個人資料存檔後，列表重抓，並顯示「評分更新中」。

**程式碼導讀**
- `backend/app/main.py` 第 33 行：`app.frontend("/", directory=FRONTEND_DIST, check_dir=False)`，讓建置好的網頁和 API 由同一個程式提供。
- `frontend/src/api/client.ts` 第 6 行：`createClient<paths>`，用產生出來的型別包住每一個 API 呼叫。
- `frontend/src/pages/ScholarshipList.tsx` 第 54 行：`refetchInterval`，評分還在背景更新時，每 5 秒重抓一次。
- `frontend/src/pages/Profile.tsx` 第 27–28 行：存檔成功後，讓兩個查詢失效。

**你可以怎麼講**：「我替獎學金 agent 做了網頁介面：React＋TypeScript 的單頁應用，建置後由 FastAPI 一起提供，所以只要開一個程式。前後端的型別由 OpenAPI 自動產生，後端改了欄位，前端編譯就會報錯。資料用 TanStack Query 抓，改了個人資料後，列表會自動更新。」

講的時候分清楚：選 React、型別自動產生、TanStack Query 是你的決定（ADR-066–071），程式是 AI 寫的。被問「為什麼不用 HTMX」，就用 ADR-066 的理由回答：你也想練前端、React 用的人最多、FastAPI 官方範本也是同一套。

**自我檢查**
1. 為什麼網頁由 FastAPI 一起提供，就不用處理 CORS？
2. 後端把某個欄位改名，前端什麼時候會發現？如果沒有自動產生型別，又會在什麼時候發現？
3. 改了個人資料後，列表為什麼會自動顯示「評分更新中」？

## 2. 混合搜尋：關鍵字＋語意，用 RRF 合併名次

**問題**
- 只用關鍵字：搜「數據科學」找到 0 筆，因為網站寫的是英文 Data Science。
- 只用語意：簡稱這類字面一模一樣的字，比對字面反而比較準（ADR-069）。

**設計**
- 同一個搜尋字做兩種搜尋：
  - 關鍵字：比對名稱、中文名稱、領域、提供單位（資料庫的 ILIKE）。
  - 語意：用第 5 天做的向量搜尋 `find`。
- 兩份名次用 Reciprocal Rank Fusion（RRF）合併：每份名次裡，第 r 名得到 1/(60+r) 分，加總後由高到低排。
- 語意搜尋不能用時（沒網路、斷路器打開、AI 出錯），就只用關鍵字，畫面上會寫「這次只用關鍵字搜尋」。
- 放棄的做法：
  - 只用其中一種：會有上面說的問題。
  - 兩種分數直接相加：兩種分數的單位不同，不能直接比。

**概念**
- **關鍵字搜尋 vs 語意搜尋**：一個比字面，一個比意思。例子：「數據科學」對上 Data Science，只有語意搜尋找得到。
- **向量（embedding）**：把一段文字變成一串數字，意思相近的文字，數字也相近。
- **RRF**：只看名次、不看分數，所以單位不同的兩種搜尋也能合併。例子：A 在兩份名次都排第 2，得 1/62＋1/62；B 只在一份排第 1，得 1/61。結果 A 排在前面。
- **優雅降級**：一部分壞了，還能提供比較少、但可以用的功能。

**程式碼導讀**
- `backend/app/features/search/fusion.py` 第 7 行：`rrf`，合併名次，不到 10 行。
- `backend/app/features/scholarships/api.py` 第 222、237 行：`keyword_ranking` 和 `semantic_ranking` 算出兩份名次；語意搜尋失敗時，API 回傳 `semantic: false`。

**你可以怎麼講**：「列表的搜尋是混合搜尋：關鍵字比對加上向量語意搜尋，再用 Reciprocal Rank Fusion 依名次合併。所以搜『數據科學』找得到寫 Data Science 的學程，簡稱也找得到。沒網路時，會自動退回只用關鍵字。」

講的時候分清楚：選混合搜尋是你的決定（ADR-069）。RRF 是業界常用的公式（Cormack 等人，2009），程式是 AI 寫的。

**自我檢查**
1. 為什麼不把關鍵字分數和語意分數直接相加？
2. 沒網路時搜尋會怎樣？你在畫面上怎麼看得出來？
3. 用 RRF 算算看：C 在一份名次排第 1、另一份排第 10，D 在兩份都排第 3，誰排前面？

## 3. 結構化金額：每筆金額附原文引用，由程式核對

**問題**：原本金額只是一格文字，AI 每次可能挑不同的數字。第 8 天發現，188 筆裡有 145 筆的官網寫了 2 個以上的歐元金額。列表也沒辦法顯示「每月多少」。

**設計**
- 抽取表格裡的金額改成清單，每筆包含：數字、幣別（ISO 4217，例如 EUR）、期間（每月、每年、總額、一次）、用途（生活津貼、學費、旅費、其他）、適用對象、逐字引用（ADR-070）。
- 程式核對兩件事：引用真的在原文裡，而且引用裡真的有這個數字。比對數字時，會處理千分位（1,400、9 000）、小數、萬和千，以及全形字。
- 列表只用核對通過的金額，優先挑「每月」的，顯示成範圍，例如「每月 310–1,400 EUR」。
- 實際跑的時候找到兩個漏洞，都是先寫出能重現的測試再修：
  - EDISS 用空格當千分位（9 000€），原本核對不過。
  - M3EP 的整個學程總額，被當成了「一次」。
- 放棄的做法：
  - 讓 AI 檢查自己有沒有寫錯：等於 AI 檢查 AI，不可靠。
  - 換算成同一種幣別：匯率會變，還要多一個資料來源。

**概念**
- **結構化輸出**：讓 AI 照固定欄位回答（Pydantic schema），程式才能檢查和排序。
- **有根據的抽取（grounding）**：每個答案附上原文引用，再用程式確認引用真的存在。例子：「每月 1,400 EUR」的引用是 “1,400 EUR per month”，原文裡找得到，引用裡也有 1400，所以算「已核對」。
- **正規化**：比對前先把不同寫法統一。例子：「9 000€」和「9,000 €」都變成 9000。

**程式碼導讀**
- `backend/app/features/scholarships/amounts.py`：
  - 第 33 行 `numbers_in`：找出一段文字裡所有的數字。
  - 第 55 行 `amount_status`：核對一筆金額。
  - 第 19 行 `_SPACE_THOUSANDS`：「空格當千分位」的規則。
  - 第 82 行 `headline`：決定列表上顯示哪個數字。

**你可以怎麼講**：「AI 抽出的每個金額都附原文引用，由程式確認引用存在，而且引用裡真的有那個數字；沒通過核對的，就不顯示在列表上。實際跑的時候找到『空格當千分位』這種格式問題，先寫測試重現，再修好。」

講的時候分清楚：把金額改成清單是你的決定（ADR-070），核對規則和修正是 AI 做的。

**自我檢查**
1. 為什麼不讓 AI 自己檢查金額對不對？
2. 「9 000€/year」原本為什麼核對不過？
3. 列表為什麼只用核對通過的金額？

## 4. 重抽 C：只補金額，其他欄位不動

**問題**：金額改成清單後，舊資料裡沒有這個清單。提示詞一改版，系統就會把每個來源整份重抽，但 AI 每次抽的結果都不太一樣：教育部的國籍從「已核對」變成了「原文沒寫」。後來查到，原文一個字都沒改的 40 筆，整份重抽後有 23 筆的截止日不同。

**設計**
- 另外寫一個只抽金額的提示詞（amounts-1）。每個來源讀一次快照原文，只填金額（ADR-074）。
- 補完後，把抽取結果記錄的提示詞版本改成最新，並記下 `amounts_from`。這是 ADR-013 快取規則的例外，所以要留下紀錄。
- 已經被整份重抽、但原文沒變的 40 筆，先從 10-27 的資料庫備份補回原本的值，再補金額。
- 結果：188 筆都有金額清單；原文沒變的 167 筆，其他欄位和備份一模一樣；共花了約 NT$15。
- 放棄的做法：
  - 照常全部重抽：已核對的欄位可能變差。
  - 全部重抽後，把變差的換回舊值：多一條規則，要測更多情況。

**概念**
- **AI 的不確定性**：同樣的輸入，每次的輸出可能不同。所以不需要重做的部分，就不要重做。
- **快取鍵**：抽取結果用「原文雜湊＋提示詞版本＋模型」當鑰匙，鑰匙沒變就沿用舊結果。改了提示詞，就要改版本號。
- **回填（backfill）**：替舊資料補上新欄位，不必整份重做。
- **冪等**：同一個指令跑兩次，第二次什麼都不會改。這次再跑一次，補了 0 筆。

**程式碼導讀**
- `backend/app/features/scholarships/amounts.py` 第 118 行 `with_amounts`：產生補完金額的新結果，其他欄位原樣保留。
- `backend/app/features/scholarships/extract.py` 第 486、492 行：`needs_amounts` 判斷哪些要補，`backfill_amounts` 負責補。

**你可以怎麼講**：「改了金額的抽取方式後，我沒讓系統整份重抽，因為實測發現 AI 重抽會讓原本已核對的欄位跟著變。我選了只補金額：用另一個提示詞只抽金額，其他欄位保留原值，再從備份補回已經被重抽的 40 筆。」

講的時候分清楚：選 C 是你的決定，選之前你看了 AI 整理的實測數據；補抽的程式、備份和還原是 AI 做的。

**自我檢查**
1. 為什麼提示詞一改，系統就會整份重抽？
2. 「把版本記成最新」為什麼是例外？如果其他欄位的規則也改了，還能這樣做嗎？
3. 怎麼證明補完金額後，其他欄位都沒變？

## 5. 每件工作被做了 4 次：RQ 的 bug

**問題**：每天的檢查要拖 1～2 天，通知晚了 16 小時。查資料發現，同一個網站一天被抓 4 次，4 次的結果都是「沒變」。

**設計**：這次最值得學的是除錯的方法。
1. 先看資料，不要猜：被判失敗的 203 件工作都有「開始時間」，代表不是沒做，而是做完之後才被判成失敗。
2. 看每件工作的執行紀錄：至少 127 件是「成功、成功、成功、成功」，代表成功之後又被重做。
3. 讀套件的原始碼：RQ 開的新程序要知道「自己只負責 1 條佇列」，才會把做完的工作從中繼佇列拿掉。
4. 找出它為什麼不知道：筆電睡超過 8 分鐘，worker 在 Redis 裡的登記資料就過期了；醒來後，閒著的 worker 心跳時只寫回一行，佇列名稱就不見了。
5. 先寫一個會失敗的測試重現問題，再修：開新程序前，登記資料缺了就補回去，只改了 3 行。修好後，每天的檢查都在當天做完。

放棄的做法：
- 換成 SimpleWorker：會失去「每件工作都用新程序跑」的好處。
- 等官方修：最新版還沒修。

**概念**
- **心跳與 TTL**：有期限的資料要定期更新，不然會消失。這次消失的是 worker 的登記資料。
- **可靠佇列**：拿起工作時先放在「托盤」（中繼佇列）上，做完才拿掉，這樣當機時工作不會不見。
- **回歸測試**：先寫一個能重現 bug 的測試，以後有人再改壞，馬上就會知道。

**程式碼導讀**
- `backend/app/features/pipeline/worker.py` 第 50 行 `fork_work_horse`：修正就在這裡。
- 測試在 `backend/tests/test_pipeline_worker.py`。它用 Redis 的第 15 號資料庫，不會碰到正在用的那一個。

**你可以怎麼講**：「我的專案每天在背景檢查 200 多個獎學金網站。我注意到排隊的工作有 160 件、通知晚了 16 小時。追查後發現，筆電睡眠讓背景程式的登記資料過期，套件把做完的工作誤判成失敗，每件重做了 4 次。先寫測試重現問題，再補 3 行修好，之後每天的檢查都在當天做完。」

講的時候分清楚：發現排隊太多、規定「先找根本原因」是你做的；除錯和程式是 AI 做的。

**自我檢查**
1. 為什麼要有中繼佇列？拿掉會怎樣？
2. 為什麼 worker 閒著時登記資料會少欄位，工作進行中卻不會？
3. 為什麼要先寫會失敗的測試，再修？

## 6. 排程規則與每日報告（第 4 段）

**問題**：一輪檢查拖過午夜時，隔天的 tick 排在收尾前面，新的一輪先開始了。結果前一輪的通知，要等新一輪約 150 件工作做完才送得出去（10-27 晚了 16 小時）。另外，你身為管理者，看不出每天的檢查到底有沒有做、為什麼。

**你的預測 vs 實際做法**

| 題 | 你的預測 | 實際做法 |
|---|---|---|
| 1. B 改了什麼 | 加一個條件，沒滿足就不做，15 分鐘後再看 | 一樣：`decide_start` 回傳「在等」時，tick 直接結束，15 分鐘後的 tick 再判斷一次 |
| 2. 要不要通知 | 每一輪都送訊息，說明有沒有做、為什麼 | 照你的做：每日報告、在等前一輪、前一輪太久，三種訊息 |
| 3. 測哪些情況 | 不知道 | 7 種，用等價類劃分和邊界值分析想出來（見下方「概念」） |
| 4. 手動指令 | 也要遵守 | 照你的做：一輪還沒收尾時，手動指令會印出原因、不排工作 |
| 逾時 | 你把 48 小時改成 24 小時 | 照你的做。代價：電腦整天沒開時，前一輪其實沒壞，也會被當成太久 |

**設計**
- 判斷寫成純函式 `decide_start(今天開始過沒, 最近一輪, 現在)`，回傳四種結果：今天開始過、在等、太久、開始。tick 和手動指令只負責查資料，再照結果做（ADR-075）。
- 三種訊息的文字也寫成純函式（`report.py`），送出時是「系統」通知：各自一則，不會被併進摘要。每種訊息有一個去重鍵（`run:id`、`waiting:日期`、`stale-run:id`），同一件事只送一次（ADR-076）。
- 放棄的做法：
  - 讓收尾和送通知插隊（C）。
  - 只在出問題時才通知：你要每一輪都知道。

**概念**
- **背壓**：下游還在忙，就先不讓上游放新的工作進來。
- **逾時（看門狗）**：等太久就不等了，避免系統永遠卡住。這裡設 24 小時。
- **等價類劃分**：把輸入分成「結果會一樣」的幾類，每類測一個代表。這裡分成：沒有前一輪、前一輪已收尾、前一輪還沒收尾。
- **邊界值分析**：門檻的兩邊和「剛好等於」都要測，這裡是 10、24、25 小時，因為 `<` 和 `<=` 最容易寫錯。
- **純函式**：只看輸入算出答案，不碰資料庫或網路，所以 7 種情況一下子就測完。
- **去重鍵**：同一件事不管觸發幾次，都只寫一則通知。tick 每 15 分鐘跑一次，「在等前一輪」的通知一天也只會送一則。

**程式碼導讀**
- `backend/app/features/pipeline/jobs.py`：第 269 行 `decide_start`、第 288 行 `skipped_days`、第 319 行 `tick`。
- `backend/app/features/pipeline/report.py`：三種訊息的文字。
