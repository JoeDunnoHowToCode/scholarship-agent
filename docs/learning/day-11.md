## 1. 持續整合：每次推送都在乾淨的環境跑一次檢查（段 1）

**問題**：之前每次推上 GitHub 前，都靠我記得在本機跑 `pytest`、`ruff`、`mypy`、`npm run build`。例如有一次 mypy 的錯誤被 `tail` 吃掉、照樣 commit 了，沒有任何東西擋下來。而且本機的資料庫裡有幾百筆真的資料，測試「在空的環境能不能過」從來沒人驗證過。

**設計**
- GitHub Actions 每次推送到 main 都跑兩個工作（ADR-099）：
  - 後端：開 PostgreSQL（和本機同一個 pgvector 映像）和 Redis → 照 `uv.lock` 安裝 → 遷移 → 種子 → 範例資料 → 測試、ruff、mypy。
  - 前端：照 `package-lock.json` 安裝 → 型別檢查與建置。
- 先在本機開一個空的資料庫 `scholar_ci` 模擬，找到 2 個只讀的測試需要「已經有獎學金和通知」。不改它們，另外加一個建虛構範例資料的指令，裡面不是從任何網站抓的內容，因為 repo 是公開的。
- 用到的 actions 都固定到某個 commit；太新（不到兩週）的版本先不用。這是供應鏈安全，和 `npm ci` 照 lockfile 安裝是同一個道理。
- CI 裡沒有任何金鑰：測試本來就不呼叫真的 AI 和網路。
- 結果：第一次就過，後端 50 秒、前端 13 秒。
- 放棄的做法：本機推送前自動檢查（可以用 `--no-verify` 略過，履歷上也不算 CI）。

**概念**
- **持續整合（CI）**：每次改動都自動在乾淨的機器上建置和測試，問題越早發現越便宜。例子：本機資料庫有資料、CI 是空的，一跑就抓到 2 個依賴本機資料的測試。
- **服務容器（service container）**：CI 裡臨時開的資料庫、Redis，跑完就丟。例子：`services: postgres` 用的是 `pgvector/pgvector:pg17-trixie`。
- **可重現的安裝**：照 lockfile 裝，每次裝到的版本都一樣。例子：`uv sync --frozen`、`npm ci`。
- **固定到 commit（pin）**：tag 可以被改指到別的程式碼，commit 不行。例子：`actions/checkout@3d3c42e…  # v7.0.1`。
- **測試資料的獨立性**：測試不該依賴某台電腦上剛好有的資料。例子：`ci_sample_data.py` 讓空的資料庫也有測試需要的最少資料。

**程式碼導讀**
- `.github/workflows/ci.yml`：兩個工作。後端的 `services`、`env`（只有連線網址、沒有金鑰）、`steps`（遷移、種子、範例資料、檢查）。
- `backend/scripts/ci_sample_data.py`：虛構的範例資料，重跑不會重複。

**你可以怎麼講**：「我用 GitHub Actions 做了 CI：每次推送都在乾淨的 Ubuntu 上開 PostgreSQL 和 Redis 容器，跑遷移、種子，再跑 313 個測試、靜態檢查和前端建置。先在本機用空的資料庫模擬，找到兩個依賴開發資料的測試，用虛構的範例資料解決，沒有把爬到的內容放進公開 repo。用到的 actions 都固定到 commit，避免供應鏈攻擊。」

講的時候分清楚：要做 CI、用 GitHub Actions 是你的決定（ADR-099）。範例資料的做法、固定到 commit、不用太新的版本，是 AI 的實作決定（「Claude 自行決定」第 5、7、8 點）。

**自我檢查**
1. 為什麼本機測試全過，CI 上卻可能失敗？這次遇到的是哪一種？
2. `uses: actions/checkout@v7` 和 `uses: actions/checkout@3d3c42e…` 差在哪裡？
3. 為什麼不直接把開發資料庫匯出一份給 CI 用？

## 2. 評估程式：同一套流程、不同模型、不寫資料庫（段 2）

**問題**：要比較 Gemini 3.5 和 3.1 Flash-Lite 哪個比較好，最直接的做法是「換模型、重抽一次」。但這樣正式資料就被改掉了；兩個模型的結果也沒辦法並排比較；而且網頁可能剛好改版，兩次看到的原文不一樣。

**設計**
- **重構**：把 `extract_source` 裡「抽取、核對、組出結果」拆成 `build_extraction`，它只算、不寫資料庫；`extract_source` 改成呼叫它再存檔。
  - 照重構的規則：先寫 pin 測試釘住現在的行為（馬上通過、單獨 commit）。
  - 重構前後各跑一次完整測試，都是 314 passed。
- **評估指令**：
  - 固定樣本：所有非 Erasmus 的來源，加上用固定亂數種子挑的 40 個 Erasmus 學程，共 57 個，存檔以後每次都用同一批。
  - 用已存的快照，兩個模型看到的原文完全一樣。
  - 每個模型各抽兩次，量得到穩定度。
- **指標都是純函式**（有單元測試）：有根據率、不完整率、穩定度、一致率；不一致清單每個來源最多 1 筆、總共最多 10 筆，讓抽查涵蓋不同來源。
- **報告只放數字**，進 git；原始結果和抽查清單有原文引用，存在本機、不進公開 repo（ADR-098）。
- 放棄的做法：直接用正式的抽取指令換模型重抽，會改到正式資料，也沒辦法並排比較。

**概念**
- **離線評估（offline evaluation）**：在不影響正式系統的情況下，用固定的資料比較不同版本。例子：`run_one` 跑完就把交易復原，資料庫什麼都沒寫。
- **控制變因**：比較時只改一個東西。例子：同一批來源、同一份快照、同一版提示詞，只換模型。
- **固定亂數種子**：亂數挑樣本，但每次挑到同一批，結果才能重現。例子：`random.Random(11)`。
- **穩定度**：同一個模型、同一份輸入跑兩次，結果一不一樣。AI 不是每次都給同樣答案，不穩定的欄位就算「有根據」也不可靠。
- **回歸評估**：之後改提示詞或換模型，再跑一次同一套，確認沒有變差。

**程式碼導讀**
- `backend/app/features/scholarships/extract.py` 第 389 行 `build_extraction`：只算、不寫資料庫。
- `backend/tests/test_extract_build.py`：重構前先寫的 pin 測試（假的 AI、暫存的網頁檔，CI 也能跑）。
- `backend/app/features/evaluation/metrics.py`：第 17 行 `grounded`，第 37 行 `agreement`，第 47 行 `disagreements`。
- `backend/app/features/evaluation/run.py`：第 48 行 `pick_sample`，第 140 行 `disagreements_markdown`，第 186 行 `run_one`（跑完復原交易）。

**你可以怎麼講**：「為了比較兩個模型，我先把抽取流程重構成『只計算、不寫資料庫』的函式：重構前先寫測試釘住行為，前後完整測試結果都一樣。評估用固定亂數種子挑出 57 個來源、用同一份已存的網頁快照，讓兩個模型各抽兩次，算有根據率、穩定度和兩模型一致率；原始結果含網站原文，所以只把數字報告放進公開的 repo。」

講的時候分清楚：用替代指標加抽查、原始結果不進 git 是你的決定（ADR-098）。重構的拆法、57 個樣本怎麼挑、指標怎麼算、不一致清單怎麼選，是 AI 的實作決定（「Claude 自行決定」第 1–4 點）。

**自我檢查**
1. 為什麼評估要用「已存的快照」，而不是重新抓官網？
2. 重構時為什麼要先寫一個「馬上就會通過」的測試？
3. 為什麼要同一個模型抽兩次？只抽一次會漏掉什麼？

## 3. 總檢查與程式規則：能用已存資料修的錯，不叫 AI 重抽（ADR-103）

**問題**：評估抽查時發現教育部的「補件期間」被當成截止日。直覺的修法是改提示詞，但版本號一改，約 250 個來源全部重抽：約 NT$65，而且穩定度只有 70%，沒問題的欄位也會跟著變。更根本的問題是，當時不知道錯有多少、是哪幾種。

**設計**
- **先量再修**：10 個 Claude sub agent 各分約 25 筆，拿抽取當時的快照原文逐筆判斷四個欄位，並替每個錯分類、標「能不能用已存的資料修」。結果是 249 筆有 128 筆有錯，206 個錯裡 57% 的線索已經存了。
- **能修的寫成程式規則**，每次抽取都套用，也對已存的資料跑一次：
  - 同一筆錢列兩次：完全一樣的只留一筆；總額＝每月×月數就去掉總額
  - 每學期的金額被存成每年：標成待確認，不自己換算
  - 截止早於開放：標成待確認，不問 AI
- **`--rules-only`**：對已存的資料重新套用規則，不呼叫 AI。執行前先備份，執行後和備份比對有變的地方。
- 放棄的做法：
  - 全部重抽：貴，而且會打亂沒問題的欄位
  - 國籍範圍矛盾的規則：程式判斷不了哪一邊對

**概念**
- **AI 輸出的後處理**：AI 的結果先經過程式檢查與修正才存。例子：`merge.clean_amounts` 把 1,400×24 的總額拿掉。
- **錯誤分析（error analysis）**：先把錯分類、數一數，再決定修哪一類、用什麼方法修。例子：分成「線索已存」和「要重抽」，決定了 ADR-103 和 ADR-105。
- **AI 當判斷者（LLM-as-judge）**：用另一個模型判斷對錯。要抽查判斷者本身，這次抽 3 個，對照原文都對。
- **和備份比對（diff）**：改資料的指令跑完，比較前後才知道改了什麼。例子：第一次跑顯示 179 筆有變，比對後發現 156 筆只是格式不同，是 bug。
- **冪等**：同一個指令跑兩次，結果一樣。修好 bug 後再跑一次，和備份只差 23 筆。

**程式碼導讀**
- `backend/app/features/scholarships/rules.py`：`redundant_totals`
- `backend/app/features/scholarships/merge.py`：`clean_amounts`
- `backend/app/features/scholarships/amounts.py`：`amount_status` 的 `period_mismatch`
- `backend/app/features/scholarships/verify.py`：`window_rule`
- `backend/app/features/scholarships/extract.py`：`recheck_rules`（`--rules-only`）
- `backend/tests/test_rules_recheck_db.py`：重新套用規則的兩個 DB 測試，第二個是重現 bug 的測試

**你可以怎麼講**：「評估時發現 AI 會把補件期間當成截止日，我沒有直接改提示詞重抽，而是先讓 10 個 sub agent 對照原文檢查全部 249 筆，把 206 個錯分類。57% 的錯線索已經存在資料庫裡，我就寫成程式規則：每次抽取都套用，也能不花 AI 費用修正舊資料。跑之前先備份，跑完和備份比對，因此抓到一個只改了格式的 bug。」

講的時候分清楚：要先總檢查、選 1-B 和 2-B 是你的決定（ADR-103–105）。檢查的方法、規則的細節、拿掉國籍矛盾那條規則，是 AI 的實作決定（計畫的「Claude 自行決定」）。

**自我檢查**
1. 為什麼不直接改提示詞、全部重抽？除了錢，還有什麼代價？
2. 「同一筆錢列兩次」為什麼可以用程式修，「漏抽申請期」卻不行？
3. 第一次跑 `--rules-only` 說 179 筆有變，你怎麼知道其中大部分是假的？

## 4. schema 加欄位、快取規則：讓 AI 分類，讓程式決定（ADR-104、105）

**問題**：總檢查裡約 50 個錯是現在的表格裝不下的資訊，例如：
- 教育部的「補件期間」被當成申請期
- 頁面寫「今年不提供 Erasmus 獎學金」，卻照樣存了申請期和金額
- 同一頁另一個補助的 300 歐元被算成這個獎學金的錢

只改提示詞叫 AI「不要抽」的話，資料庫裡什麼都不留，事後查不到原因。另外，提示詞一改版，約 250 個來源就會全部重抽。

**設計**
- **schema 加三個欄位**：
  - 申請期的 `kind`：申請獎學金、只有入學、補件、繳費、其他
  - 獎學金的 `offered`：有、沒有、不清楚，附引用
  - 金額的 `for_this`：是不是這個獎學金的錢
- **AI 只負責分類，程式決定怎麼用**：
  - 只有 `kind=scholarship` 的日期會變成申請期、送截止提醒
  - `offered=no` 不產生申請期
  - `for_this=false` 的錢不寫進金額描述
  - 被排除的資訊照樣存著，詳細頁另外列成「其他時程」
- **預設值讓舊資料維持原本的行為**：重抽前沒有新欄位的資料，當成申請獎學金、是這個獎學金的錢、不清楚有沒有開。
- **快取規則（ADR-104）**：判斷要不要重抽時不再看提示詞版本，只看原文和模型。要用新版重抽，就指定來源並加 `--force`。
- 放棄的做法：
  - 只改提示詞的文字（2-A）：被排除的資訊看不到
  - 改版就全部重抽（ADR-013 原本的做法）

**概念**
- **向後相容（backward compatibility）**：新程式要能讀舊資料。例子：`kind` 預設是 `scholarship`，所以 249 筆舊資料不用馬上重抽也能正常運作。
- **分類與決策分開**：AI 擅長讀文字分類，程式擅長照規則決定。例子：AI 填 `kind=document`，`save_cycles` 決定不建申請期。
- **快取失效的範圍**：快取鍵放什麼，決定什麼東西一改就要重算。例子：把提示詞版本拿出快取鍵，改提示詞就不再全部重抽。
- **衍生資料要跟著來源算**：「最早截止日」是從申請期算出來的。如果它把補件日期也算進去，系統會以為已經有截止日，就不去補抓 PDF 了。

**程式碼導讀**
- `backend/app/features/scholarships/schemas.py`：`WindowKind`、`Offered`、`kind`、`for_this`、`offered`
- `backend/app/features/scholarships/extract.py`：
  - `save_cycles`：只建 `kind=scholarship` 的申請期
  - `earliest_deadline`
  - `extract_source`：快取規則與 `force`
- `backend/app/features/scholarships/amounts.py`：`own`
- `backend/app/features/scholarships/api.py`：`other_dates`、`offered`
- `backend/prompts/extract/13.md`、`section/13.md`、`outline/9.md`
- `frontend/src/pages/ScholarshipDetail.tsx`：「這次不提供」和「其他時程」

**你可以怎麼講**：「總檢查發現有一類錯是 schema 表達不了的，例如補件期間被當成申請期。我在 schema 加了日期種類、今年有沒有開、這筆錢是不是這個獎學金的三個欄位：讓 AI 只負責分類，由程式決定要不要建申請期、送提醒，被排除的資訊照樣存著，查得到原因。新欄位有預設值，舊資料不用馬上重抽。我也把提示詞版本拿出快取鍵，以後改提示詞不會自動讓 250 個來源全部重抽，只重抽指定的。」

講的時候分清楚：選 2-B（加欄位）和 1-B（只重抽指定的）是你的決定（ADR-104、105）。欄位的值、預設值、`offered` 放在長文件第一輪判斷，是 AI 的實作決定。

**自我檢查**
1. 為什麼新欄位要有預設值？如果沒有，舊資料會發生什麼事？
2. AI 把真的申請期分類成 `document`，你在網頁上看得出來嗎？在哪裡？
3. 拿掉提示詞版本之後，改了提示詞，舊的來源什麼時候才會用新版重抽？

## 5. 獎學金說明與重新檢查：改完要再量一次（段 5、段 4）

**問題**：
- 詳細頁沒有一段告訴你「這是什麼獎學金」。
- 抽取修正做完之後，要怎麼知道它真的變好了，而不是只是看起來變好？

**設計**
- **說明是獨立的一步**，有自己的提示詞和版本號：2–3 句中文，每句附原文引用，再核對三關：
  - 數字要在引用裡
  - 引用要在原文裡
  - AI 判斷引用撐不撐得起這句話
  - 只顯示通過的句子
- **排在全部重抽之後才補抽**，否則重抽會換掉整個 `extracted`，說明被洗掉。每天的檢查抽完也會自動補。
- **重新檢查**：同樣 158 筆、同一份指示，比較重抽前後。結果是：
  - 金額 42% → 69%
  - 錯誤 206 → 156
  - 截止日沒有變好：自費輪次被標成申請獎學金，加上 extract-14 可能改錯了 3 筆
- 放棄的做法：只看評估指標（有根據率）就宣布完成。有根據不等於正確，評估指標也看不出分類錯。

**概念**
- **回歸（regression）**：修一個地方，另一個地方變壞。例子：上次全對的 30 筆，重抽後 12 筆有錯，部分是 AI 每次結果不一樣，部分是新的分類錯。
- **前後比較要用同一批資料、同一份指示**：控制變因，不然分不出是程式變好還是題目變簡單。
- **判斷標準會影響數字**：這次的指示改成「判斷網頁會顯示什麼」，自費輪次從不算錯變成算錯。報告要寫清楚，不能直接說退步。
- **補救要小範圍**：芬蘭那幾筆只重抽 10 筆，這是 ADR-104 的用法。但補救本身也可能錯，所以還是要量。

**程式碼導讀**
- `backend/app/features/scholarships/summary.py`：`check_sentences`（三關）、`make_summary`、`ensure_summary`、`needs_summary`
- `backend/app/features/pipeline/jobs.py` 第 198 行：抽完就補說明
- `backend/app/features/scholarships/extract.py`：`run_backfill`（金額和說明共用）、`--backfill-summary`

## 9. 被擋的來源自動再試：分清楚「暫時」和「永久」（ADR-116，總檢查段 2）

**問題**：11-18 早上，EACEA 目錄抓到第二頁時回了 429（請求太頻繁）。程式把它標成「需人工」，從此每天跳過，目錄新增的學程都進不來。另外還有 29 個來源也是被擋一次就再也不抓，而且沒有任何方法恢復。

**設計**
- 你選了 C：429 七天後再試，403 三十天後再試；robots.txt 禁止和 captcha 照舊等你處理。
- 實作：
  - `sources` 加一個欄位 `retry_on`：哪天再試。
  - 伺服器有回 `Retry-After`（請多久後再來）就照它，但至少隔一天、最多七天。
  - 再試沒被擋就清掉標記，回到每天檢查。
  - 翻頁來源（EACEA 目錄）每頁隔 15 秒（原本 5 秒）。
  - 每日報告列出「哪天自動再試」或「要你處理」。
- 放棄的做法：
  - 原本計畫寫「另外存被擋的日期」，實作時改成直接存「哪天再試」。排程只需要後者，少一個欄位，也少一次換算。
  - 被擋就馬上換一種方式抓（例如換 User-Agent）：違反 ADR-028「被擋就停、不換手法」。

**概念**
- **HTTP 429 與 Retry-After**：429 代表「你太快了」。伺服器可以附一個標頭說多久後再來，可能寫秒數（`172800`），也可能寫日期。例如測試裡 `172800` 秒算成 2 天後再試。
- **暫時錯誤和永久錯誤要分開**：同樣是「被擋」，429 等一下就好，captcha 等再久都一樣。如果用同一套處理，不是太早放棄，就是一直去打擾。
- **退避（backoff）**：被拒絕後隔一段時間再試，而且有上限和下限。這裡的下限是 1 天、上限是 7 天，所以就算伺服器說等 30 天，我們最多等 7 天就再試。
- **假的網站（MockTransport）**：測試抓取器時不連真的網路，換一個假的 httpx 傳輸層。例如測試裡的假網站對每一頁都回 429 加 `Retry-After: 172800`。

**程式碼導讀**
- `backend/app/features/sources/fetch.py`：`retry_on`、`days_to_wait`、`still_blocked`、`fetch_interval`、`blocked_since`，以及 `fetch_source` 被擋時與完成時的兩段
- `backend/app/core/fetch/base.py`：`BlockedError.retry_after`
- `backend/app/core/fetch/http.py`：把 `Retry-After` 標頭帶出去
- `backend/app/features/pipeline/jobs.py`：`due_source_ids` 被擋的分支、`process_source` 開頭的 `still_blocked`
- `backend/app/features/pipeline/report.py`：`BLOCK_REASONS` 與「今天被擋」那幾行
- `backend/migrations/versions/6d3f0981afdd_sources_retry_on.py`：加欄位，並把現有的標記改成再試日期
- 測試：`tests/test_blocked.py`、`tests/test_blocked_db.py`、`tests/test_pipeline_messages.py`

**你可以怎麼講**：「爬蟲被網站擋的時候，我把原因分成暫時和永久兩種。429 是太頻繁，照伺服器的 Retry-After 退避，最多一週後再試；403 一個月試一次；robots.txt 和 captcha 是網站明確不讓機器人抓，就不再試、交給人處理。再試成功會自動回到每天檢查，每日報告也會寫哪天再試。」

- 只傳入 237 個已加入、啟用中的來源。重抽指令沒指定來源時，連排除的來源也會抽，既浪費錢，又會把封存的資料寫回來。
- 跑完由同一個腳本接著做收尾（refresh、去重），再開回背景程式。電腦用 `caffeinate` 保持醒著。
- 結果用 SQL 分組來看，不靠抽樣幾筆的印象：
  - 列表 244 → 239 筆
  - 沒有申請期 77 → 70 筆，每筆都有原因
  - 地區名額拆成多筆的：0
  - 申請方式知道的：125 筆（52%）
- 放棄的做法：重抽完直接寫「完成」。只看完成數 237，看不出申請方式有一半是「不知道」。

**概念**
- **重抽前停背景程式（避免競爭）**：兩個程式同時改同一筆資料叫「競爭狀況」（race condition），後寫的會蓋掉先寫的。先停掉一個最簡單。
- **用分組計數驗收**：`group by` 把每種結果數出來，一眼看出哪一類特別多，再往那一類追。
- **診斷實驗**：申請方式被擋下的 74 筆，我把同一句引用分別拿去問核對的 AI：「這句支持哪一種申請方式？」這只呼叫 AI，不寫資料庫。結果分成兩群：
  - 約 13 筆的引用寫「自動列入評選」，核對的 AI 說支持「和入學一起申請」。所以被擋，是因為抽取的 AI 填了別的。
  - 其他約 60 筆的引用沒寫怎麼申請，擋下是對的。
- **沒存下來就無法診斷**：核對沒通過時，AI 原本填的值被改成 unclear，原值沒有留下。所以只能推測 AI 填了什麼。要能追查，就要把原值也存下來。
- **AI 判斷會飄**：同一句問兩次，16 筆裡有 3 筆答案不同。單次核對的結果有雜訊，要看整體的數字。

**程式碼導讀**

## 17. 重新檢查：分清楚「變差」還是「標準變嚴」（總檢查段 8）

**問題**：重抽後拿 11-17 的同一批資料再檢查一次。國籍從 85% 掉到 76%，看起來是改壞了。但這次判斷用的標準多了一條新規則：地區名額要寫成類別。如果判斷的尺變長了，分數掉下來不一定代表資料變差。

**設計**
- 判同樣的 141 筆，11-17 那次的判斷結果拿來直接比，用同一個算法：正確 ÷（正確＋部分對＋錯）。
- 另外 17 筆沒重抽，資料沒變，所以不判。
- 國籍拆成兩個數字：照舊規則算是 85%，和 11-17 一樣；掉的 16 筆全是新規則 AI 沒做到。
- 往下追「從對變錯」的 20 筆，找到一個真的錯：類別的地區代號寫反了，14 筆獎學金被判國籍不符。這是段 7 改出來的。
- 也找到我排的原因順序有錯：隨入學一起審、但原文說日期還沒公布時，應該先說「還沒公布」。先寫重現的測試（red），再改順序（green）。
- 放棄的做法：只報總分。總分看不出是哪一條規則、哪一種錯。
- 寫反的地區代號你選 A（ADR-120）：存檔時，類別的代號如果全都在整筆「排除」的群組裡，程式就拿掉。現有 20 筆用一次性腳本修，不呼叫 AI，重新評分後 15 筆都不再判國籍不符。
  - 腳本先試跑：第一次寫「會修正 360 筆」，數字不合理。查出是舊資料沒有地區代號欄位，腳本補空清單也算改變。改成只動有代號的類別後是 20 筆，套用後再試跑一次是 0。

**概念**
- **回歸（regression）**：改了 A，結果把原本好好的 B 弄壞了。這次就是：段 7 為了地區名額，讓類別可以附地區代號，結果非歐盟獎學金的類別被附上 EU，評分判反了。
- **同一把尺**：比較前後時，算法、範圍、標準都要一樣。標準變了，就要另外算一個「照舊標準」的數字。
- **先試跑（dry run）**：改資料的腳本先只印出會改哪些，數字合理再套用；套用後再跑一次應該是 0，代表改完了、也不會重複改。
- **判斷者之間的干擾**：6 個判斷者共用暫存資料夾，輔助腳本互相覆蓋。所以要檢查每份輸出的 id 都和輸入對得上。下次給每個人各自的資料夾。

**程式碼導讀**
- `backend/app/features/scholarships/cycles.py`：`no_date_reason`，先看「還沒公布」再看「隨入學一起審」
- `backend/tests/test_no_date.py`：新加的那一個例子
- `backend/app/features/matching/score.py`：`hard_checks` 裡用類別的 `nationality_groups` 判斷。寫反的代號就是在這裡被當成「只給這些地區」

- `docs/eval/2026-11-21-audit.md`：數字與原因
